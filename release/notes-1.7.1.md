## 一、Lunar 物料下载接入启动器下载器

以前 Lunar 的物料（客户端 jar、纹理、许可文件、JRE）走的是 `PCL.Core` 里一份裸 `HttpClient`：不走代理、不跟随设置里的 HTTP 模式、没有分段下载、没有限速，失败只在日志里留一行。

现在 Core 暴露 `DownloadDispatcher` 钩子，应用层启动时把 `FileDownloader` 注册进去，物料下载整包交给它：

| 能力 | 之前 | 现在 |
| --- | --- | --- |
| 代理（HTTP / SOCKS） | 不支持 | 跟随启动器设置 |
| HTTP 版本协商 | 固定 | 按文件大小自动选 |
| 大文件分段下载 | 无 | 有，慢连接会自动拆分续传 |
| 限速 / 连接数 | 无 | 跟随「下载」设置 |
| 重试 | 单地址 3 次 | 多镜像轮试 + 3 轮重试 |

`DownloadFirstAsync` 会把**完整的候选地址列表**交给通道，所以 JRE 那种「官方 CDN + 备用 CDN」的物料现在真的会两条都试。

没注册通道的场景（单元测试、Core 单独使用）仍然退回原来的内置下载，行为不变。

### 物料准备进度条

Lunar 启动页在物料准备阶段多了一条 4px 的进度条，按「已完成文件数 / 总文件数」铺。

- 条数确定的阶段（许可、纹理、资源、jar）正常显示
- 条数不定的阶段（JRE 解压）和启动后自动隐藏
- 换阶段一定重绘，同一阶段百分比没变就不刷

### 实机验证（1.8.9 真实物料）

| 检查项 | 结果 |
| --- | --- |
| 物料地址 `HEAD` | `200`，`Content-Length` 正常 |
| 物料地址 `Range: bytes=0-0` | `206 Partial Content`，分段下载可用 |
| 下载完成后 SHA-1 | 与清单一致 |
| UA `PCL2 PCLCE` | CDN 正常接受，无 403 |
| 纹理索引 / 纹理文件 | `200`（464 个文件） |

## 二、44 个红测试清零，其中 4 个是真 bug

`dotnet test` 现在是 **569 / 569 通过**，之前有 44 个红。查下来不全是环境问题：

| 现象 | 影响 | 修法 |
| --- | --- | --- |
| `HashStorage.PutAsync` 存成 0 字节文件 | 缓存、大文件存储写入的文件是空的 | 算完哈希流已经在 EOF，写文件前归位 |
| `EncodingDetector` 恒判 UTF-8 | 缓冲区声明了却从没读流，全零样本永远通过校验 | 真读样本再 round-trip |
| 缓存「亚秒过期」删不掉 | `datetime()` 只到秒级精度，100ms 过期的条目永远留在库里 | 改成 `"O"` 格式字符串比较（定宽 UTC，字典序即时间序） |
| `HashCache` 并发写报 `SQLITE_READONLY` | 50 并发下 13/15 轮复现，批量算哈希会随机失败 | 单持久连接 + 全操作串行，实测 0/15 |

过期统计（`GetStatsAsync`）原来还在用 `datetime('now')` 计数，和删除逻辑口径不一致，统计里「已过期」永远是 0 条 —— 这版一起统一了。

其余红的是测试环境问题：SQLite 连接池没清就删目录、EventBus 生命周期 `Context` 没点亮、测试宿主没注册代码页提供方、DoH 的 SRV 测试域名已经停止发布记录。

## 已知问题

- 进度条按「文件条数」算，单个超大文件（JRE 压缩包）下载期间百分比会停着不动，属于预期
- 首次用某个版本时，Genesis 仍要先把原版客户端补到 `%APPDATA%\.minecraft`（100–200 MB），这段是它自己做的，PCL 只能等，没有进度
- 物料下载失败时的重试轮次从「单地址 3 次」变成「多地址各 3 轮」，极端网络下最坏耗时比之前长
